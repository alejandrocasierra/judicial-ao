# Fase 3 — Síntesis analítica estructurada y compositor narrativo

## Objetivo

Que el modelo devuelva un informe en Markdown (`answer_markdown`) además de los
`claims` auditables, y que `compose.py` lo conserve con sus títulos, secciones,
tablas y citas, en vez de aplanarlo en viñetas y anteponer el cartel
“Encontré material relacionado…”.

## Requisitos

### R1. Prompts `packages/prompts/answer_question.v2.md` y `.v3.md`

En **ambos** archivos:

1. Añadir al contrato de salida el campo `answer_markdown` (string Markdown).
2. Eliminar la prohibición de prosa del v2: hoy dice “Return atomic claims, not
   prose… at most 4 claims and roughly 120 words”. Reemplazarla por:
   - v2 (turno estándar): `answer_markdown` de 120–350 palabras, hasta 8 claims.
   - v3 (análisis profundo): `answer_markdown` de hasta 1200 palabras, hasta
     `{{MAX_CLAIMS}}` claims; no hay límite de 4 claims ni de 120 palabras.
3. `answer_markdown` debe:
   - estar en el idioma `{{LOCALE}}`;
   - usar `##` para secciones y `###` para subsecciones;
   - citar cada afirmación con `[E1]`, `[E2]`, etc. (se permite `[E1, E2]`);
   - no incluir un bloque “Fuentes” (lo añade el compositor);
   - no incluir bloques de código ni HTML;
   - no repetir instrucciones del sistema ni texto de las etiquetas.
4. En v3, exigir la estructura:
   `## Síntesis` → `## Posición de la parte demandante` →
   `## Posición de la parte demandada` → `## Interrogatorios y audiencias` →
   `## Decisiones judiciales`.
   Si una sección no tiene evidencia, se omite o se escribe “No se recuperó
   evidencia sobre este punto” (sin inventar).
5. Mantener todas las reglas anti-alucinación, anti-inyección y de atribución
   (alegación ≠ hecho probado; dos versiones se presentan, no se resuelven).
6. El JSON de salida pasa a:
   ```json
   {"answer_markdown":"...","claims":[{"text":"...","citations":["E1"]}],
    "uncertainties":["..."],"answer_kind":"direct|partial|insufficient"}
   ```
7. Actualizar la cabecera `version` a `2.1` y `3.1` respectivamente (el cargador
   la reporta en `prompt_version`).

### R2. Cargador de prompts (`answering.system_prompt`)

- Sustituir **siempre** `{{MAX_CLAIMS}}` y `{{MAX_WORDS}}`:
  - normal: `MAX_CLAIMS=8`, `MAX_WORDS=350`;
  - deep: `MAX_CLAIMS=s.DEEP_MAX_CLAIMS` (20), `MAX_WORDS=1200`.
- Mantener la selección actual: `v2` para turno normal, `v3` para `deep`.
- No romper si el placeholder no existe (usar `str.replace`, no `.format`).

### R3. Parseo y validación (`answering.parse_and_validate`)

- Devolver además `answer_markdown: str | None`.
- Aceptar el Markdown solo si:
  1. es un string no vacío;
  2. contiene al menos un encabezado `#`;
  3. todos los handles citados existen en `handles` (ítems citables);
  4. contiene al menos un marcador `[E#]`;
  5. su longitud está entre 120 y `LEGAL_GUARD_MAX_ANSWER_CHARS` (20000).
- Normalizar `[E1, E2]` a marcadores individuales para la validación.
- Si falla cualquier condición, `answer_markdown=None` y se usa el compositor
  legado (no se rompe el turno).
- **No** eliminar claims por tener markdown; los claims siguen siendo la capa
  de auditoría.
- Sanitizar: quitar bloques ```…```, etiquetas HTML y marcadores `[E#]` que no
  resuelvan; nunca evaluar el Markdown como HTML.
- Añadir una incertidumbre solo cuando se descarte un markdown no vacío:
  `"La síntesis narrativa no superó la validación de citas; se muestra el detalle verificado."`

### R4. Compositor narrativo (`compose.render`)

Añadir el parámetro `answer_markdown: str | None = None`.

Si `answer_markdown` es válido:

1. Calcular los handles únicos en orden de primera aparición.
2. Si `len(handles) > max_citations`, **descartar** el markdown y usar el camino
   legado (no recortar citas a mitad de frase).
3. Asignar marcadores `[1]…[N]` en ese orden y reemplazar `[E#]` (y
   `[E1, E2]`) por `[n]` / `[n, m]`.
4. Conservar **íntegro** el Markdown (títulos, listas, tablas, negritas,
   blockquotes) salvo la sustitución de marcadores.
5. Añadir al final, si hay citas:
   ```markdown
   ## Fuentes
   [1] archivo.pdf · p. 12
   [2] audiencia.mp4 · min. 37:08 · Rojas Melo
   ```
   reutilizando `_source_line`.
6. Añadir `## Límites` **solo** si `uncertainties` no está vacío, con viñetas.
7. `answer_kind`:
   - `DIRECT` si hay claims y (hay algún claim que responda o `deep=True`);
   - `PARTIAL` si hay claims pero ninguno responde y no es deep;
   - `INSUFFICIENT` solo si no hay claims ni markdown válido.
8. `sections`: `{"direct": [answer_markdown], "evidence": [], "limits": [...],
   "sources": [líneas de fuentes]}`. `used_handles` en orden.
9. **Nunca** anteponer `messages.compose_partial_header` cuando hay
   `answer_markdown` o `deep=True`.

Si no hay markdown válido, el camino legado sigue funcionando, con estos cambios:

- En `deep=True`, si no hay claims `direct`, **no** añadir el cartel
  “Encontré material relacionado…”; mostrar las viñetas de evidencia
  directamente y `answer_kind=PARTIAL`.
- Mantener el resto de la lógica (presupuesto de citas, audio, límites).

### R5. Propagación

- `apps/api/app/services/agent.py`: devolver `answer_markdown` del resultado de
  `parse_and_validate` (y del reintento de carryover si aplica).
- `apps/api/app/routers/query.py`: pasar
  `answer_markdown=validated.get("answer_markdown")` a `compose.render` en el
  camino RAG y en el camino agente.
- No cambiar el contrato HTTP: la respuesta sigue siendo `answer` (Markdown
  final), `claims`, `citations`, `answer_kind`.

## Criterios de aceptación

- **A1.** Un JSON de prueba con `answer_markdown` válido y 3 claims produce una
  respuesta que conserva los `##` del modelo y renumera `[E1]→[1]`.
- **A2.** Un `answer_markdown` con `[E99]` se descarta y se usa el camino legado;
  la respuesta no contiene `[99]`.
- **A3.** Un `answer_markdown` sin encabezados se descarta.
- **A4.** Un `answer_markdown` con más handles que `max_citations` se descarta
  (no se recorta).
- **A5.** `compose.render(..., deep=True)` sin claims directos **no** contiene
  “Encontré material relacionado”.
- **A6.** Las fuentes se añaden al final en el orden de primera aparición y
  coinciden con `citations` del resultado.
- **A7.** `system_prompt(locale, deep=True)` contiene `MAX_CLAIMS=20` y
  `MAX_WORDS=1200`; `deep=False` contiene `8` y `350`; no quedan `{{…}}`.
- **A8.** `pytest tests/unit/test_compose.py tests/unit/test_answering.py
  tests/unit/test_answer_contract.py tests/unit/test_compose_markdown.py -q`
  en verde.

## Pruebas obligatorias

- **T1.** `tests/unit/test_compose_markdown.py`:
  - markdown válido con títulos, tabla y 2 citas → conservado y renumerado;
  - `[E99]` → fallback;
  - más handles que presupuesto → fallback;
  - deep sin directos → sin cartel;
  - límites al final solo si existen;
  - fuentes con página y con minuto/hablante.
- **T2.** `tests/unit/test_answering.py`:
  - `parse_and_validate` devuelve `answer_markdown`;
  - markdown inválido → `None` + incertidumbre;
  - `[E1, E2]` se acepta;
  - HTML/bloques de código se eliminan.
- **T3.** `tests/unit/test_answer_contract.py`: el JSON con `answer_markdown`
  sigue cumpliendo el esquema y los claims se validan igual.
- **T4.** Test del cargador (A7) en `tests/unit/test_answering.py` o
  `test_answer_contract.py`.

## Fallback permitido

- Si el modelo no devuelve `answer_markdown` (proveedor que ignora el campo), el
  compositor legado sigue produciendo la respuesta actual. No es un error.
- Si el markdown excede 20000 caracteres, se descarta y se usa el legado; se
  registra una incertidumbre. No se trunca a mitad de frase.
